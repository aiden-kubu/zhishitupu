## 四、实施要求

### 1. 使用编辑对象身份判断，不能只比较资料 ID

`saveDocEditor` 已在函数开始处保存局部快照：

```ts
const editor = docEditor.value
```

保存完成和捕获错误时，把现有的同 ID 判断：

```ts
docEditor.value?.doc.id === editor.doc.id
```

改为同一个编辑对象判断：

```ts
docEditor.value === editor
```

原因：用户可能关闭旧弹窗后重新打开同一份资料。两次编辑的资料 ID 相同，但编辑对象不同；旧请求只能影响它开始时的旧编辑对象。

至少覆盖以下两处：

- 成功后关闭弹窗。
- 失败后写入 `docFormError`。

不要增加时间戳、请求编号、全局状态库或新的抽象；对象身份判断已经足够。

### 2. 每个成功响应立即同步资料列表

保存顺序仍保持：

1. `updateDocumentMetadata`
2. 人工校对值有变化时，再调用 `setDocumentVerification`

第一步成功后立即执行：

```ts
replaceDocument(updated)
```

不要等第二步也成功后才统一更新。第二步成功后，再用第二个响应执行一次 `replaceDocument(updated)`，以同步最新 verification。

这样即使第二步失败，服务端已经保存的标题和生命周期也会马上反映在资料列表中。

### 3. 区分整体失败和部分失败

- 如果第一步元数据请求失败，保留普通的“保存失败”提示。
- 如果第一步成功、第二步人工校对请求失败：
  - 不关闭当前弹窗。
  - 只在 `docEditor.value === editor` 时显示错误。
  - 错误文案必须明确表达：`标题和生命周期已保存，但人工校对状态保存失败`。
  - 可以在该文案后附加 `ApiError.message`，但不能再显示成全部保存失败。
  - 保留用户当前勾选值，允许再次点击保存重试。
- 如果两步都成功，正常关闭仍在显示的原编辑弹窗。

使用最小的局部 `try/catch` 或等价控制流完成，不抽取新 composable、服务层或通用错误框架。
