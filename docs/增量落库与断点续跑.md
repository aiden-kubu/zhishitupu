# 增量落库与断点续跑

2026-09-14 交付。资料解析完成后，AI 抽取与 AI 复审都改为「边做边落库、断了接着跑」，一批失败不再让此前所有模型调用作废。

## 为什么需要

原实现是「全部批次成功后一次性写候选」，而候选写入还排在 AI 主题分类之后。整本教材量级资料需要数百次模型调用，任何一次超时、限流或输出不合规都会让全部已完成部分丢失，重试从第 1 批重新开始。

现场证据（任务 #938《textbook.zip》，2026-09-14）：161 批抽取全部成功（16:16–17:15，约 1 小时），随后在主题分类阶段报 `LLM_BAD_RESPONSE`「资料包含超过 12 个独立主题，请拆分资料后重试自动分类」；由于候选只在分类成功后写入，这 161 批成果全部作废，重试意味着再花一小时重复调用模型。批次越靠后失败，损失越大。

## 机制

### 抽取：按批落库

- 新表 `extraction_batch_results`（V8 迁移，随 `ingestion_jobs` 级联删除）保存每一批的成果：批次指纹、该批真实 chunkId 顺序、校验后的规范化抽取结果（`entities`/`relations`）、实体/关系条数、模型名。
- 每一批在**模型返回并通过校验后立即写入**，写入发生在执行该批的工作线程里，与批次顺序无关。因此并行批次中任何一个失败，其他已完成批次的成果依然保留。
- 任务启动时按批读取断点行：指纹一致的批次直接复用（不调用模型），缺失批次才送模型。

### 批次指纹只认内容

指纹 = 批次内片段条数 + 每条片段长度 + 片段内容的 SHA-256，与 chunkId 无关。这样：

- **重新解析同一份文件**（例如任务失败后点「重试任务」，单元与片段被删除重建、chunkId 全变）→ 内容不变 → 指纹不变 → 批次复用；复用时按位置把证据编号重映射成本次的真实 chunkId。
- **OCR 文本变化、重新分段、资料被替换** → 指纹变化 → 该批作废重抽，不会把旧证据挂到新片段上。
- 批次计划变短（片段变少）时，超出的旧批次行被删除。
- 复用同样要过一遍校验（`ExtractionPayloadParser`），断点数据与模型输出按同一不可信输入处理；证据无法映射到本次片段时宁可重抽。

### 复审：复用既有判断

复审结论（判断、理由、模型、时间）本来就在每批复审后写入候选行的 `edited_payload_json.aiReview`。现在重跑时先读取这些结论：**同一模型**且已判定的候选不再送审，只复审缺失项。换模型后不复用旧结论（结论按模型名匹配）；候选被重抽（行删除重建）时旧结论自然失效。

## 重试与重抽的行为

| 入口 | 行为 |
|---|---|
| 处理中心「重试任务」（`POST /api/processing/jobs/{id}/retry`） | 有候选 → 续跑 AI 复审；解析产物完整（有片段且无 `NEEDS_OCR`/`OCR_SKIPPED`/`OCR_FAILED` 单元）→ 保留单元与片段，从抽取阶段续跑，复用已落库批次；否则按原逻辑清理产物、从解析阶段整体重跑 |
| 处理中心「重新识别知识」（`POST /api/processing/jobs/{id}/extract`） | 同步校验后异步抽取，复用既有 chunks 与已落库批次 |
| 同一入口带 `force=true` | 断点数据立即作废，真正重新抽取全部批次 |
| 候选已就绪（任务进入 `AWAITING_REVIEW` / 入库完成） | 抽取事务内清除断点数据；此后再发起抽取不会命中旧成果 |

图片单元处于 `OCR_SKIPPED`/`OCR_FAILED`/`NEEDS_OCR` 时**不续跑抽取**，仍走清理重跑：用户配置视觉模型后点「重试任务」必须能重新 OCR，续跑会跳过这一步（ING01 的既定行为）。

## 进度与界面

- 抽取进度以「已就绪批数」为起点：复用 380/400 批时一进任务就显示 380/400，之后按补齐的批次递增；`processed_units`/`total_units` 仍是批数。
- AI 复审的进度单位由「批」改为「候选条数」。
- 处理中心任务卡在 `FAILED`/`CANCELLED` 且存在断点批次时提示「已保留 N 批抽取结果，点『重试任务』将从断点继续，这些批次不会再调用模型」；接口字段为 `stagedBatches`。

## 运维与排查

- 查看某任务的断点批次：`SELECT batch_index, entity_count, relation_count, model, updated_at FROM extraction_batch_results WHERE job_id = ? ORDER BY batch_index;`
- 清理某任务的断点数据（不影响候选与正式知识）：`DELETE FROM extraction_batch_results WHERE job_id = ?;`
- 任务成功进入 `AWAITING_REVIEW` 后该表不应有该任务的行；有残留说明当时清理失败，可用上面的 DELETE 或直接 `force=true` 重抽。
- 回退整个特性：删除 V8 迁移与 `extraction_batch_results` 表即可（只丢失断点数据）。代码回退见 `docs/变更记录.md` CHG-0076。

## 不覆盖的部分

- 主题分类（`organization.plan`）本身没有断点：它是实体级的一次数次调用，失败后重试只要秒级——因为抽取批次已落库，不会重复消耗抽取调用。
- 断点数据不跨任务复用：换一份资料或新建任务即重新开始。
- 指纹按「内容不变」判定复用，OCR 每次结果不同（模型有随机性）时对应批次会重抽，这是有意为之。
- 复审结论按模型名匹配，因此失败后更换默认模型会重新复审全部候选。
