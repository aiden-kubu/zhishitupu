# 新上传资料自动整理

> 最新用户决策：人工审核已取消，现由 AI 对照证据复审并自动入库；下方早期人工审核记录仅为历史。现行规范见《AI自动复审入库.md》。

2026-09-13 用户确认：先整理新上传内容，自动归入已有库或新建多个库；不合并、拆分已有知识库。

默认流程：上传资料 → 解析与视觉识别 → 分段抽取知识 → AI 比较已有主题并命名、分类 → 审核候选 → 按分类入库。用户无需预先命名或创建知识库，可选指定已有库以沿用原流程。

相近主题复用现有库；多个独立主题可以创建多个库；同一个知识点可属于多个主题。关系保持全局连接，原始文档和证据片段不复制。已有库名称不被 AI 改写；知识库页面可手动修改名称。

## 接口与数据

- `POST /api/documents` 的 `libraryId` 改为可选。省略时创建明确标示「待 AI 识别」的临时库，记录自动整理标记。校验失败、重复上传或事务失败不留下新库和上传文件。
- 分类阶段使用现有默认模型，输入抽取的知识名称、定义以及已有库名称、简介。模型输出仅作为分类建议数据，不接受资料内的指令。
- 校验每个知识点均被覆盖、库 ID 属于输入白名单、名称长度和格式有效。最多 12 个主题组；候选按每批最多 100 个分类，后续批次参考前面主题并按已有库 ID/新库同名合并，完整校验每批知识点覆盖。已有库超过 200 个时明确提示指定库，避免静默丢失上下文。
- V6 新增 `auto_document_imports`（自动导入及并发文件去重）、`document_topic_assignments`（文档—候选键—知识库）、`organization_mutex`（自动建库串行查重）。没有新增第三方依赖。
- 分类与全部候选同一事务落库。失败保留原文件与任务供重试，不写入半成品分类或新库。成功后删除本次上传的空临时库；重复抽取复用已创建的同名库。
- `GET /api/documents/{id}/organization` 返回主题库及候选数量，审核中心展示。
- 审核通过的新增或复用节点都写入对应的 `library_nodes`。来源定位仍使用同一份文档和 chunks。
- 文档列表与各库资料计数包含共享关联。删除一个库时，若原资料还属于其他库，保留原资料并调整主库引用。

## 大文档抽取等待与进度（2026-09-13）

任务 #63 首次抽取在等待模型约两分钟后返回 LLM_UNREACHABLE，解析出的 401 个片段保留。模型连通性测试成功。结构化抽取现使用不超过 8192 token 的输出预算、至少 120 秒的读取等待；对 DeepSeek 官方接口显式关闭思考模式（普通问答保留原配置）。批次数在开始时写入，每完成一批更新 processed_units，80–94% 用于抽取，94% 显示主题分类，95% 等待审核。前端同时显示文档名和正在等待的批次。

恢复时还发现单批实体截断为 30 个会导致后续关系引用不存在的编号。现保留限额内的完整实体和关系，超过安全上限则明确报错，不再先截实体再校验关系；提示词要求每批最多 30 个核心实体和关系。新增 entity_31 → entity_29 回归测试，116 项后端测试、前端构建通过。完整文档仍需依次处理全部批次，不将单批成功视为整本处理完成。

## JSON 失败批次恢复（2026-09-13）

任务 #63 曾在第 25/53 批因非法 JSON 中断。抽取现在对 LLM_BAD_RESPONSE 在当前批次最多尝试 3 次，重试要求更精简的完整 JSON 与正确字符转义；每次仍严格校验实体、关系和真实证据编号。认证错误不重试，批次重试之间检查取消。连续失败的信息包含批次编号。

LlmClient 检测 finish_reason=length，拒绝将长度截断响应当作完整结果；不猜测补齐 JSON。此前失败响应未留存，因此不能断言当时一定由输出截断导致。既有成功批次尚无持久化缓存，恢复仍重新抽取全部批次，复用已解析文本。
