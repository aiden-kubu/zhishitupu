# 智能助手模块审计与重规划

日期：2026-09-22。状态：规划稿，尚未实施；按用户后续要求，架构已调整为多 Agent 协作。

审计基线：当前工作区代码，包含尚未提交的智能助手、学习路径、智能测评、学习进度及其他在途修改。依据前后端实现、接口、数据库迁移和已有测试进行静态审计；没有操作生产环境、调用付费模型、执行业务写入或开展浏览器交互验收。下文的性能、交互效果和验收指标均为目标，不是已经验证的结果。

## 1. 核心结论与产品定位

当前「智能助手」本质是独立页面中的单节点问答面板。它已经具备原文检索、带来源回答、临时追问、停止等待、模型错误提示等基础，但尚不具备覆盖项目全过程所需的业务上下文、状态查询、跨模块引导和操作协作能力。

建议定位为：**贯穿知识建设与学习应用全过程的项目助手，负责理解当前对象、解释真实状态、提供有依据的回答，并协助用户完成下一步。**

产品形态确定为：**一个智能助手工作区，背后由总控 Agent 与多个专业 Agent 共同完成用户目标。** 单个 Agent 也能调用多个工具、执行多步任务；本项目采用多 Agent 的价值在于领域分工、独立上下文、可并行探索、交叉复核和跨阶段交接。

它需要同时覆盖两条主线：

- 知识建设：环境准备 → 建库与导入 → 解析/OCR/抽取 → 自动复审与入库、人工纠偏 → 图谱维护 → 质量分析 → 补充资料。
- 学习应用：确定学习目标 → 生成路径 → 阅读原文与图谱 → 讲解和练习 → 正式测评 → 更新学习进度 → 调整学习重点。

“不可或缺”的验收含义是：每一个业务阶段都能从助手获取当前状态、原因解释和有效的下一步；跨阶段协作由它串联。各业务模块仍拥有自己的操作页面和业务规则，助手不可用时，导入、复审和图谱等基础功能仍应能使用。

### 1.1 本次规划保留的既有决策

1. **临时对话、不保存聊天历史。** 当前代码明确记录了此前用户决策：关闭、切换节点、刷新即清空；不访问旧会话表。规划沿用这一原则，不默认引入历史会话、长期记忆或后台保存对话。
2. **相关主题允许模型补充讲解。** 资料事实必须可追溯；资料未写到的相关解释与例子可以补充，但要明确标识。现有“仅基于知识库回答”文案应改为与真实策略一致。
3. **复用现有业务服务。** 继续使用现有 Vue、Java 服务和数据库；第一阶段不以更换技术栈、引入向量数据库或新的代理框架为前提。
4. **沿用项目当前使用模式。** 当前学习档案是固定的 `local-default`。本规划不擅自增加账号体系，但也不把当前共享学习状态称为已具备多用户个性化隔离。

### 1.2 多 Agent 适配判断

项目适合采用“总控协调 + 专业 Agent + 受控业务工具”的混合架构，理由直接来自当前业务结构：

- 资料建设、质量复审、知识研究、学习辅导、测评分析需要不同的上下文和判断标准，能够形成稳定的职责分工。
- 不同教材、不同章节、不同候选批次之间存在可并行的研究任务；阅读与比较的中间成果能够以证据清单交接。
- 导入到学习的长目标需要多个阶段接续，单次节点问答接口无法承载完整任务状态。
- 当前 Java 项目已经有可复用的领域服务，可先在同一个后端进程中实现多个 Agent 角色和调度器，不需要为每个角色拆一个微服务。

当前 `ChatService` 仍是一次检索后调用模型，`LlmClient` 接口只收发文本，未暴露工具调用循环。`ExtractionService`、`AiReviewService` 和 `LearningPathService` 是已有业务服务，不能因它们调用了 AI 或内部存在并发就声称项目已经实现多 Agent。[E02][E13]

第一版定义总控加五个专业角色。角色数量与运行实例数量分开：一次简单问答可能只执行知识研究角色；比较三本书可以创建三个同角色研究实例；所有实例都受同一任务预算约束。五个角色不要求五种不同模型，也不要求每次全部启动。

## 2. 已有能力与关键问题

优先级定义：P0 为达成新定位或保证操作结果正确的前置条件；P1 为基础版本必须补齐的能力；P2 为后续体验与质量提升。这里不是安全漏洞评级。

| 编号 | 优先级 | 代码事实与影响 | 规划处理 |
|---|---|---|---|
| A01 | P0 | 助手只有 `/api/nodes/{nodeId}/chat`，没有节点就不能提问；新用户导入前、处理失败时均无法获得业务帮助。[E01][E02] | 引入不依赖节点的统一助手入口，支持项目、库、资料、任务、节点和学习对象。 |
| A02 | P0 | 聊天只读取节点、邻域、原文，未接入处理状态、复审决策、洞察或学习状态。[E02] | 把知识问答、业务状态查询、操作协作拆成三类能力，按意图调用对应服务。 |
| A03 | P0 | 界面承诺“仅基于知识库”，提示词却允许相关主题的模型补充。[E03] | 回答分为资料依据、系统事实、补充讲解和操作建议，统一文案与返回契约。 |
| A04 | P0 | 检索在所有已完成且在用的资料中匹配，仅把同库结果排在前面；“当前节点”不等于严格限定当前库。[E04] | 范围必须可见且由服务端执行过滤；跨库作为显式范围，返回实际使用的范围。 |
| A05 | P0 | 测评由前端算分并上传汇总，后端直接按分数推进当前阶段；没有题目、答案、阶段版本绑定，且推进分支没有复用 `visitedAt` 检查。[E05] | 正式测评由服务端绑定试卷、阶段与提交记录并计分，统一阶段完成规则后再允许助手驱动此闭环。 |
| A06 | P0 | 保存新学习路径会先删除当前路径，外键级联删除阶段和测评记录。[E06] | 区分“新建”“调整”和“替换”；保留版本及旧进度，先预览差异再应用。 |
| A07 | P0 | AI 复审会自动入库；有候选结果的任务“重试”也会触发该链路。AI 搜索扩展会直接写入节点/关系。[E07][E08] | 操作卡展示实际副作用，不能把这些操作包装为只读诊断或普通回答。 |
| A08 | P1 | 独立助手页仅取全局概览的 30 个节点，无搜索、分页或库筛选；只额外尝试补入当前学习节点。[E01] | 首页以用户任务为入口，节点选择改为可搜索的上下文选择器。 |
| A09 | P1 | “原文定位”只是展示返回的短摘录，没有请求原文单元；已有单元接口返回分段，但分段 DTO 未提供数据库 chunkId，尚不能直接与聊天引用精确匹配。[E09] | 补齐稳定分段标识与版本/hash，再实现原文侧栏和准确高亮；首版无需依赖 PDF 图片预览。 |
| A10 | P1 | 模型收到最近临时历史，但检索仅接收当前问题；“它、两者、继续比较”没有检索级指代解析。[E02][E04] | 在当前临时对话内解析指代并展示实际检索对象；歧义时询问，不默认跨范围。 |
| A11 | P1 | API 接受两层邻域，但提示词过滤为直接关系；关系统一输出箭头，未保留原始主客体方向。[E10] | 用 source/relation/target 明确方向；两跳回答提供真实路径和截断提示。 |
| A12 | P1 | 切节点清消息但不清输入草稿；失败/停止的用户消息仍可能进入后续历史；超长回答也可能在下一轮超过后端单条历史上限。[E11] | 草稿随上下文清理；按成功轮次组织历史，限制整体预算和单条大小。 |
| A13 | P1 | 桌面与手机图谱面板是独立实例；查看详情、切路由会卸载临时对话，断点切换存在隐藏实例继续运行的风险。[E12] | 同一打开周期使用一个控制器；详情/原文在当前表面打开；关闭和切换范围仍遵守清空规则。 |
| A14 | P1 | 正式测评目前优先按当前节点与邻域规则拼题，前置数据不足或失败会保留/回退通用固定题；保存结果失败被吞掉。[E05] | 明示“当前知识点测评”或“通用演示练习”；无正式题目时不记入阶段完成，保存失败可恢复。 |
| A15 | P1 | 等待时只有动画；停止会中断浏览器请求，代码未建立向上游模型传播取消的协议。[E11][E13] | 分阶段反馈；明确“停止回答”和“取消业务任务”的区别，不承诺停止等待即停止上游计费。 |
| A16 | P2 | 回答按纯文本展示，无结构化操作卡、表格呈现、复制/重试、反馈入口；输入缺少完整的发送语义和长度反馈。[E14] | 先补可访问输入、答案结构和重试，再按需求增加安全 Markdown 与表格渲染。 |

这些问题不意味着所有基础能力需要重做。应继续复用现有的原文分段与证据关联、默认模型配置、错误脱敏、请求取消与过期响应丢弃、任务状态机、复审事务、学习数据表，以及已有聊天和检索测试。

## 3. 职责边界

### 3.1 助手负责什么

| 能力层 | 必须做到 | 事实依据 |
|---|---|---|
| 理解当前情境 | 知道用户所在页面、选择的库/资料/任务/节点/学习阶段；显示取材范围 | 路由与用户选择提供对象标识，服务端查询真实对象 |
| 查询与解释 | 回答知识问题，解释任务失败、复审原因、图谱关系和进度 | 原文证据、结构化业务查询、有效的学习记录 |
| 规划与建议 | 提出导入步骤、修复方案、学习计划、补充资料和图谱调整建议 | 当前数据 + 明确标注的模型建议 |
| 操作协作 | 生成可审阅操作卡、打开正确页面、调用允许的业务操作并跟踪结果 | 服务端操作注册表、对象版本、业务服务返回值 |
| 下一步衔接 | 从结果继续定位到原文、任务、复审记录、图谱或学习阶段 | 经过验证的对象 ID、业务路由和后端状态 |

### 3.2 原业务模块继续负责什么

- 知识库：库与资料的生命周期、文件、元数据和归属。
- 处理中心：解析、OCR、抽取、任务进度、恢复与取消。
- AI 复审：候选质量判断、去重和最终入库事务；人工修订是规划中的模块职责，现有后端/旧组件有相关能力，但当前页面主要展示 AI 结论，需补齐可用入口和覆盖规则。
- 图谱工作台：图形探索、节点/关系的正式编辑、来源与状态。
- 学习路径：正式路径、版本与阶段顺序；测评模块负责题目、作答、判分；学习进度负责真实记录的聚合。
- 数据洞察：确定口径的统计查询；系统设置负责模型档案、密钥和配置生效。

助手使用这些能力，不在聊天模块复制一套数据库写入、判分或入库逻辑。聊天中的“建议已生成”不等于“已保存”，“任务已受理”不等于“已完成”。

### 3.3 回答边界

1. 资料事实：引用实际返回的原文证据，支持定位。
2. 系统事实：来自业务接口，显示对象、状态与查询时间；必要时显示统计范围与截断情况。
3. 模型补充：允许与当前知识/任务相关的解释、例子和学习建议，明确标记，不挂原文引用。
4. 草稿建议：新增节点、关系、练习、学习路径等在执行前均为草稿；不得混入正式图谱或正式成绩。
5. 范围外问题：说明本助手覆盖知识建设、学习与项目操作，给出可用入口；不能把系统操作问题误判为“当前节点主题无关”而直接拒答。
6. 数据不足：区分“未选范围”“正在处理”“未形成正式知识”“检索未命中”“资料本身不足”，每种状态给出对应下一步。

不把任意网页浏览、计算机控制、任意 SQL/脚本执行、无限自主循环和第三方平台操作纳入首版。

本表每一行都属于完整模块的验收范围。分期只影响能力深度，不允许遗漏整段流程。

| 场景/原模块 | 用户的典型问题 | 助手应交付什么 | 可复用基础 | 要补的能力 |

| 知识库规划 | “这批课程资料放哪里？” | 库与资料概况、归属建议、重复/缺失提示；创建或调整草稿 | LibraryService、文档元数据、organization | 资料/库上下文、归属建议预览、目标库明确选择 |

| 资料治理 | “这份资料过时了，整理标题和标签” | 解释资料归属、标题、标签、归档/过时状态和校对记录；提出或按授权应用元数据修改 | 文档 metadata、tags、verification、organization 接口 | 展示生命周期变更对取材的影响；AI 建议与人工校对分开；资料删除等缺失页面入口明确列为待补 |
| 解析/OCR/抽取 | “为什么停在这里？应该重试还是重新抽取？” | 当前阶段、进度、错误、是否存在检查点/候选，给可执行恢复路径 | ProcessingService、IngestionPipeline、ExtractionCheckpointStore | 错误到建议的映射；状态再校验；区分等待、重试与强制抽取 |
| 自动复审、人工纠偏 | “为什么这条关系被拒？这批能入库吗？” | 候选与证据对照、AI 决策解释、修订/合并建议、入库影响 | ReviewService、AiReviewService、ai-decisions | 复审上下文、证据预览、批量影响清单；明确复审可能自动入库 |
| 图谱探索与维护 | “这两个概念有何关系？这条边方向对吗？” | 带方向的关系与路径、来源、跳转聚焦；修改建议和差异 | GraphService、NodeService、EdgeService、SearchService | 多节点上下文、路径查询契约、图谱数据来源/审核状态展示 |
| AI 搜索扩展 | “库里没有这个概念，补一个” | 先区分讲解与新增；明确目标库、来源为 AI、待核验状态和关联建议 | AiExpandService、AiExpandStore | 草稿/入库边界；不把“解释一个概念”自动转换成正式扩展 |
| 知识问答与原文阅读 | “对照这两份资料解释这个概念” | 按指定范围检索、比较异同、标注各自来源、打开原文 | RetrievalService、document units/chunks | 库/文档/跨库过滤、多轮检索、稳定证据标识、原文阅读侧栏 |
| 学习路径 | “按我的目标安排学习步骤” | 基于库、目标、水平、可用时间提出路径，说明顺序和依据 | generateLearningSteps、LearningPathService | 服务端路径草稿与校验、预览、版本管理；时间是估计而非实测 |
| 讲解与练习 | “我没听懂，用例子讲，再给两道题” | 分层讲解、提示、练习、答案解释和针对性追问 | 当前问答、节点与原文 | 练习结构；与正式测评分离；练习不会自动改变成绩 |
| 正式测评 | “测一下当前阶段掌握得如何” | 生成/获取阶段题目、进入作答、服务端评分、错因与复习建议 | 当前规则出题、learning_assessment_attempts | 试卷/题目版本、提交标识、答案判定、阶段绑定、防重复推进 |
| 学习进度 | “我接下来该学什么？上次哪里错了？” | 当前阶段、完成依据、有效成绩、薄弱点和后续建议 | LearningPathService、LearningProgressView | 测评详情与薄弱点读取接口；区分缓存与最新状态 |
| 数据洞察、质量改进 | “为什么孤立节点多？优先补什么？” | 根据真实统计解释分布、孤立节点和待复审量，提出改进任务 | InsightService、节点与任务查询 | 范围/采样说明；可定位的问题清单；趋势类结论需历史数据后再做 |
| 日常故障与恢复 | “模型离线，哪些工作还能继续？” | 区分后端/数据库/模型故障，保留确定性的查询、跳转和人工操作入口 | health、模型测试、统一错误码 | 非模型降级、重试入口、请求编号与诊断摘要；不把密钥或完整原文写入诊断日志 |

注意：现有资料上传会继续启动处理，抽取还可自动执行复审入库。用户明确选择这一流程后，沿用一次授权覆盖该任务；不在每个内部阶段重复弹确认。失败恢复必须根据当前状态判断这次动作究竟会重跑哪一段。[E07][E15]

### 4.1 Agent 分工与交接成果

| 角色 | 负责的目标 | 可使用的主要业务能力 | 交付给其他角色的成果 | 写入边界 |
|---|---|---|---|---|
| 总控 Agent | 理解完整目标、拆分任务、安排依赖与并行、处理分歧、汇总进展与结果 | 能力就绪摘要、任务调度、成果读取、操作预览 | 任务计划、分工、范围快照、授权范围、统一结果 | 不自行扩大授权；通过执行器提交已校验操作 |
| 资料建设 Agent | 建库与归属规划、上传衔接、处理恢复、资料元数据与生命周期 | Library/Document/Processing/Organization 服务 | 资料清单、处理任务编号、可用状态、恢复方案 | 复用既有流水线；不重复启动其中的抽取/复审步骤 |
| 质量治理 Agent | 解释复审结论、核对证据、发现冲突/孤立节点、提出纠正建议 | Review/AiReview/Insight 与原文查询 | 问题清单、证据核对结果、修订建议、尚未解决的冲突 | 不代签人工校对；入库与修订遵守领域状态机 |
| 图谱研究 Agent | 多资料检索、概念讲解、关系与路径分析、教材比较、知识扩展草稿 | Retrieval/Search/Graph/Node 与原文单元查询 | 带来源的知识结论、关系路径、比较报告、候选补充知识 | 解释不触发扩展入库；图谱更改只输出受控操作提案 |
| 学习教练 Agent | 学习目标分析、路径设计、通俗讲解、练习与复习安排 | 图谱/原文查询、路径草稿与版本服务 | 路径草稿、教学解释、练习、调整建议 | 不覆盖既有路径历史，不把练习成绩记入正式测评 |
| 测评分析 Agent | 组织正式测评、解释错因、分析有效成绩与学习进度 | 试卷/作答/判分服务、学习阶段与测评记录 | 测评任务、有效结果、薄弱点、供教练使用的复习依据 | 客观计分与阶段推进由服务端规则执行，Agent 不能自行填分解锁 |

系统配置与简单诊断是总控和相关专业角色共享的受控能力，初版不为每个设置项建立 Agent。复杂 OCR/模型故障由资料建设 Agent 结合诊断工具分析；普通状态查询可以直接由程序返回。以后只有在任务评测证明有价值时再拆独立诊断角色。

每个专业角色具备目标、独立工作上下文、允许工具、完成条件和预算，并能够根据工具结果决定下一步。仅切换角色名称、串联固定提示词或让多个模型重复同一答案，不计为本规划的多 Agent 验收成果。

### 4.2 一个目标如何由多个 Agent 接续完成

示例目标：“把这两本教材整理成图谱，比较差异，给我安排七天学习并测评。”

1. 总控解析为资料建设、资料比较、质量检查、学习安排和正式测评子任务，确认目标库及必要的学习目标；文件仍通过真实上传入口选择。
2. 资料建设 Agent 调用现有导入处理流程，跟踪解析、抽取、自动复审和入库。总控可同时读取现有学习进度、检查模型能力，不必等导入结束后才做准备。
3. 资料达到规定可用状态后，两个图谱研究实例分别研究教材 A/B；质量治理 Agent 可并行检查本次入库结果与证据完整性。检查结论不再次触发已有自动复审任务。
4. 总控汇总两份研究结果，交给图谱研究角色进行差异比较；依据已确认的知识范围，学习教练提出七天路径，测评分析角色可并行起草入门测评。
5. 正式路径保存后，测评绑定实际路径与阶段版本；需要用户真实作答，再由服务端计分并更新阶段。之后测评分析角色提供薄弱点，学习教练据此给出复习建议。
6. 最终交付包含资料处理状态、质量问题、教材差异、学习路径及测评入口/实际结果。仍待用户作答的测评显示“等待作答”，不能把整个任务标成学习已完成。

可并行的是独立取证、分析、草拟和只读检查。上传→解析→抽取→复审→入库，以及作答→判分→更新阶段，按数据依赖和业务规则接续。同一正式对象的相互冲突写入不得同时执行。

## 5. 信息架构与用户体验

### 5.1 入口结构

建议把侧栏「智能助手」移到「主工作区」，与「图谱工作台」并列；它服务知识管理和学习两个方向，不宜继续仅归在「智能学习」内。保留 `/assistant`，不再增加同名顶层模块。

使用同一个能力内核，提供两种展示方式：

- 独立助手页：处理跨模块目标、多对象比较、较长解释和方案审阅。
- 页面内助手侧栏：在资料、任务、候选、节点和学习阶段旁就地提问；“在助手中展开”可以转到完整页。

每个模块提供与当前对象相关的入口，例如“解释失败原因”“核对这条关系”“讲解当前知识点”“分析本次错题”。入口自动携带对象 ID，用户不需要重新复制标题、错误码或原文。

### 5.2 独立页面布局

从现有“固定节点列表 + 聊天面板”改为“当前范围 + 对话/任务结果 + 按需证据侧栏”。

```text
智能助手                         当前范围：项目 / 某知识库 / 当前对象
我可以帮助你建设知识库、探索图谱、推进学习。对话仅本次打开有效。

当前对象：教材 A   处理任务：#...   [更换范围] [清除上下文]
──────────────────────────────────────────────────────────
用户目标、回答、证据、操作预览、任务状态     原文/对象详情（按需打开）

依据原文 [...]    模型补充 [...]           完整单元 + 高亮分段
建议动作 [查看影响] [执行一次]              来源状态/资料名称/页码
──────────────────────────────────────────────────────────
输入问题或描述目标                         [发送]
```

首页快捷卡保持少量并随状态变化：没有资料时展示“开始导入”“配置模型”；存在失败任务时展示“解释处理失败”；有当前学习阶段时展示“继续学习”“复习薄弱点”。这些卡来自真实状态，不显示虚构的推荐或完成数。

全局模式默认不把全部资料灌入模型；先根据问题确定需要的范围。空项目也能回答系统使用问题。节点选择器支持搜索和库过滤，不能用概览前 30 项冒充完整知识点目录。

### 5.3 上下文与临时对话规则

| 事件 | 预期行为 |
|---|---|
| 从业务页打开助手 | 显示所带对象及范围，开启该范围的临时对话 |
| 打开原文或对象详情 | 在当前助手内打开侧栏/移动端子视图，不触发关闭对话 |
| 桌面与手机断点切换 | 同一次打开使用同一控制器，不产生两个并行问答实例 |
| 更换节点、资料、库或任务范围 | 明示将开始新临时对话；有内容时提供轻量提示，清空旧草稿、消息和在途回答 |
| 多对象比较 | 在开始提问前建立显式的多对象范围，整个问答受此范围约束 |
| 折叠/关闭、新对话、刷新 | 清空临时内容；文案可见；不暗中改为浏览器存储或服务端历史 |
| 跨页面跳转 | 携带业务对象和目标动作，不默认转移聊天记录；可带显式的待提问文本供用户发送 |
| 业务任务已提交后关闭助手 | 聊天清空；真实业务任务按自己的生命周期继续，可在处理中心重新查看 |

“全流程覆盖”通过业务对象、服务和任务记录实现，不依赖保存聊天。若将来决定跨关闭保留聊天，必须作为独立产品变更处理。

### 5.4 回答与操作体验

- 普通知识问题先给直接回答，必要时展开“资料依据”“补充讲解”；不用在每条短答上堆满卡片。
- 有引用时，编号与原文位置对应；点击可读取完整单元，高亮实际 chunk。首版展示解析文本；原文件/PDF/图片预览需要另补文件访问与渲染能力。
- 操作卡固定显示目标对象、将发生的变化、可能影响、预计是否调用模型、执行入口和最终状态。
- 任务进度展示真实阶段，例如“正在读取任务”“正在检索原文”“正在生成回答”；没有后端事件就不虚构百分比。
- 输入支持中文输入法、明确发送按钮标签、约定的快捷键、换行和字数反馈；发送失败保留可重试内容，重试不重复业务操作。
- 消息区具备屏幕阅读器状态播报、可见键盘焦点；手机输入不被软键盘遮挡，弹层支持返回/关闭并恢复焦点。
- 移动端采用主对话与原文子视图切换，避免多个窄侧栏叠加；滚动以消息区域为主，实际高度和焦点行为要用浏览器验收。

### 5.5 多 Agent 协作的用户可见形态

保留一个主输入框，用户描述目标后看到“本次协作”区域。默认由总控选择角色，也允许用户指定“主要请学习教练处理”，总控仍可在任务范围内调用其他必要角色。

```text
目标：比较两本教材，生成七天学习方案

本次协作                       任务结果
资料建设    已完成              两份资料已入库 · 查看任务
图谱研究 A  正在分析            教材 A · 当前取材范围
图谱研究 B  正在分析            教材 B · 当前取材范围
质量治理    已完成              发现 2 项待核查问题 · 查看依据
学习教练    等待研究结果        依赖：教材比较结果

[展开任务分工] [查看成果] [停止后续协作]
```

上例状态和数量仅为设计示意，实现时全部读取实际任务记录。用户能查看每个角色的职责、使用对象、关键证据、产物和失败原因；主对话由总控汇报，避免所有角色同时刷屏。展示可核验的操作与进展摘要，不以展示模型内部推理过程作为产品能力。

每个目标有独立任务卡和范围快照。用户在前台继续问另一个问题，不得悄悄修改已经提交任务的对象；可以查看正在执行的任务。关闭临时对话依旧清空聊天，已明确提交的业务协作任务可凭任务卡或业务入口查看结果。

## 6. 操作权限与执行边界

原则是按实际效果分类；不是看到 `GET/POST` 或“重试”字样就判断风险。

| 类别 | 示例 | 交互与执行约束 |
|---|---|---|
| 查询、解释、导航 | 查任务状态、解释复审、看原文、打开图谱 | 可直接执行；数据来自业务接口，必要参数不明时先定位对象 |
| 草稿生成 | 学习计划建议、节点/关系编辑建议、练习 | 可直接生成并明确未保存；模型不可伪造正式 ID |
| 明确且可撤回的小改动 | 单个资料标签/标题等 | 用户已经明确对象和内容时可直接执行并反馈；对象不明则先给选择，保留撤回或更正入口 |
| 会启动工作或改变正式数据 | 导入并处理、重试、重新抽取、AI 复审入库、AI 扩展、保存路径、批量审核 | 展示整体影响；用户的明确点击或明确授权可覆盖列明的整个任务；执行前校验当前状态，避免重复确认与重复执行 |
| 删除、替换、配置密钥等敏感变更 | 删除库/资料/节点、替换学习路径、改默认模型、编辑密钥 | 首版助手给出影响说明；有原模块入口则定位，无入口则明确未开放并列入待补，不能生成虚构操作链接；密钥只在设置表单处理。后续接入前需有明确对象、影响预览与可验证执行结果 |

其他必要约束：

1. 模型只生成已登记操作的结构化参数，服务端负责允许列表、对象存在性、范围、状态和参数校验；不接收任意 URL、SQL 或代码作为可执行工具。
2. 文档、图谱字段和历史文本都是数据，不得把其中的“指令”作为执行授权。
3. 执行前预览绑定目标 ID、版本/状态和参数摘要；对象变化后旧预览失效，需要刷新影响。
4. 写操作具有幂等标识；重复点击、网络重试和恢复查询返回同一执行结果。多步流程逐步记录结果，不承诺跨所有领域的一次性事务或通用撤销。
5. 超时不等于执行失败；进入“结果待确认”，通过任务/操作编号查询实际结果后决定是否重试。
6. “停止回答”只作用于回答请求；“取消处理任务”必须单独显示其业务效果。已经入库的数据不能靠停止聊天撤销。
7. 现有公开访问/缺少账号鉴权的部署决策不在本次擅自改动。操作确认与允许列表只约束助手行为，不能代替整个系统的身份鉴权；多人独立学习与管理授权不应被宣称已支持。[E16]
8. 资料的“人工已校对”只由用户明确确认的校对行为产生，助手可解释或提出核验建议，不能用 AI 判断代签人工核验；人工修订与自动复审结论冲突时需定义覆盖顺序并保留可追溯记录。[E18]

## 7. 技术落地方案

### 7.1 服务组织

```text
独立助手页 / 各模块上下文入口
             ↓
统一上下文与临时对话控制器
             ↓
总控 Agent + 任务调度器（依赖、预算、取消、结果检查）
       ┌─────┬─────┬─────┬─────┐
       ↓     ↓     ↓     ↓     ↓
    资料建设 质量治理 图谱研究 学习教练 测评分析
       └─────┴─────┴─────┴─────┘
             ↓
证据与成果交接 / 受控工具 / 操作预览与统一执行器
             ↓
现有 Library / Document / Processing / Review / Graph / Learning / Settings 服务
```

总控负责规划与综合，调度器负责确定性执行约束；专业 Agent 依据各自任务使用工具。它们不拥有新的图谱入库事务或成绩判定逻辑。确定性的状态查询、系统引导和导航尽量不依赖模型调用；复杂解释、比较和建议再调用模型。首版每个目标限制总任务数、并发实例、模型轮次、资料量和超时，避免无限循环。

### 7.2 建议的上下文契约

以下为拟新增协议，不代表当前接口已经存在：

```text
AssistantContext
  surface: workspace | contextual
  routeName
  scope: project | libraries | documents | nodes | job | learningStep | assessment
  libraryIds / documentIds / nodeIds
  jobId / pathId / stepId / assessmentId
  objectVersions
  requestId
```

前端仅提供对象标识和用户显式选择。服务端解析对象、校验范围，重新读取必要属性；不能相信前端传来的“该任务已完成”“得分 100”“有权操作”等结论。

临时 `history` 继续随请求发送，但按完整成功轮次截取；失败、取消、工具执行状态和本地提示不能混为模型的事实记忆。资料内容与历史分别限额。每轮证据使用稳定 `sourceId`，呈现编号只属于当轮，避免上一轮的 `[1]` 被理解为本轮另一篇原文。

### 7.3 建议的返回契约

```text
AssistantResponse
  requestId
  runId / taskSummaries[] / artifactRefs[]（有协作任务时）
  status: answered | needs_input | evidence_missing | action_ready | failed
  effectiveScope
  answerBlocks[]: source_fact | system_fact | model_explanation | recommendation
  citations[]: sourceId, documentId, unitIndex, chunkId, hash, excerpt
  relatedObjects[]
  actionProposals[]: actionType, targetIds, params, impact, preconditions
  limitations[]: incomplete_retrieval | stale_data | unsupported_action ...
```

操作执行结果单独返回操作/任务编号、受理状态、已完成步骤和可继续入口，不能从一段自然语言中解析“已执行”。不要求每条回答都包含全部区块。

### 7.4 建议的接口演进

| 拟议接口 | 用途 |
|---|---|
| `GET /api/assistant/capabilities` | 返回可用能力、缺少配置、范围支持和降级状态；不暴露密钥 |
| `POST /api/assistant/ask` | 接收上下文、问题与临时历史，统一知识/业务回答 |
| `POST /api/assistant/runs` | 提交需要多步协作的明确目标，创建范围固定的协作任务并返回 runId |
| `GET /api/assistant/runs/{id}` | 返回真实分工、依赖、子任务状态、证据与成果引用；不返回其他任务的聊天 |
| `POST /api/assistant/runs/{id}/cancel` | 停止尚未开始的协作步骤，向在途步骤发取消请求；已受理领域任务单独报告其取消结果 |
| `POST /api/assistant/actions/preview` | 生成执行影响、前置条件与短期有效操作凭据 |
| `POST /api/assistant/actions/execute` | 执行已校验的操作，带幂等标识；复用领域服务 |
| `GET /api/assistant/operations/{id}` | 查询操作是否受理、完成、失败或结果待确认 |
| 既有 `/api/processing/jobs/{id}` 等 | 长任务继续使用原业务状态接口，不复制第二套任务状态 |

流式回答可作为兼容增量：先保证非流式返回及错误恢复正确，再引入状态事件/文本增量。旧 `/api/nodes/{nodeId}/chat` 在迁移期保留适配，避免图谱侧栏同时失效。

### 7.5 检索与证据

1. 把 `RetrievalService` 从强制单节点扩为明确范围；先按资料状态和用户选择过滤，再召回、排序、去重和裁剪。
2. 区分来源准备状态与图谱审核状态。知识问答默认沿用正式可用来源；检查解析/OCR质量时可在用户选定资料内读取已准备单元，并标记其尚未完成的处理状态，不混称为已审核知识。
3. 相关代词通过临时历史解析；保留查询原文与解析后的对象供诊断，跨范围时不静默扩大。
4. 修复当前同库优先但非范围过滤、候选前 80 条可能提前丢失相关结果等问题；用评测决定是否升级检索机制，不预设必须引入新数据库。
5. 图谱事实保留方向、节点来源与复审状态；两跳解释包含具体路径。AI 搜索生成的 active 节点不能因状态 active 就视为有原文证据。
6. 服务端校验引用 ID 存在且属于本轮证据；无效编号不显示为有效引用。该校验只能证明引用存在，是否支持对应论断还要用样例评测与人工核验。
7. 跨资料冲突并列呈现，指出各自来源，不凭生成文本自动裁定哪个教材正确。
8. 单元分段接口补充稳定 `chunkId` 与版本/hash，聊天引用返回同一套标识；当前 `ChunkView` 只有顺序索引、正文、hash 和偏移，不能把 `chunkIndex` 当数据库 `chunkId`。重新解析后引用需重新校验，旧引用失效时不能错高亮新的内容。[E09]

### 7.6 学习闭环必须补齐的领域能力

- 将可复用的路径生成/验证能力放到服务端或形成统一契约；目标相关性、先修关系和难度可解释，明确图谱截断和估计学习时长。
- 路径调整产生新版本，保留已经完成的阶段与测评；如果确需从头开始，明确显示重置效果，不沿用当前删除整条路径的普通保存语义。
- 测评持有 `assessmentId + pathId + stepId + version`；提交答案而非客户端总分；由服务端判分，提交具备幂等性。
- 阶段完成走唯一规则：图谱学习/访问条件、有效测评条件与当前阶段状态一致，不能在不同接口中形成两套门槛。
- 通用固定题只作为演示或练习，不能给任意当前节点记合格；聊天生成题默认属于练习。
- 提供测评详情、错题主题和有效成绩读取能力；助手按这些数据给复习建议。现有访问标记不等于真实学习时长或掌握程度。
- 当前档案明确为本项目共享/本地档案；多人模式需要另行完善身份与档案归属后再开放。

### 7.7 存储与可观测性

不启用旧 `chat_sessions/chat_messages`，不保存原始聊天。必要的业务草稿、操作执行记录、路径版本和测评记录属于业务数据，应与聊天历史明确区分。

操作记录可只保留操作类型、对象 ID、参数摘要、授权/执行时间、结果、幂等标识、错误码和关联任务；默认不记完整提示词、资料正文或模型密钥。回答日志主要记录延迟、检索命中量、错误类别和请求编号。具体保存周期在实现时按项目已有运维规则确定。

模型不可用时，能力就绪检查、读取任务、原文查看、模块导航仍工作；只有生成解释和建议进入降级状态。设置中的主动连接测试可能调用模型，不能把它作为每次打开助手都会静默执行的健康检查。

### 7.8 多 Agent 运行机制

#### 7.8.1 任务与成果契约

```text
AssistantRun
  runId, structuredGoal, scopeSnapshot, authorizedActions
  status, createdAt, deadline, totalBudget, cancellationRequested

AgentTask
  taskId, runId, role, objective, dependencyIds
  inputRefs, permittedTools, expectedOutput, completionCriteria
  scopeSnapshot, objectVersions, stepBudget, status

AgentResult
  taskId, outcome: completed | partial | needs_input | failed
  findings, evidenceRefs, artifactRefs, actionProposals
  unresolvedQuestions, limitations, usage, observedVersions
```

总控基于结果判断是否继续、补查或交接，调度器检查依赖是否满足。证据与产物使用稳定标识，接收方按需读取，不把全项目数据和其他 Agent 全部中间对话复制给每个角色。实际应用的数据版本必须可追踪。

子 Agent 可以提出需要另一种专业能力，由总控统一调度；初版不允许子 Agent 无限递归创建团队。各角色不能互相授予更大的读写范围。

#### 7.8.2 模型与工具循环

在现有 Java 服务内增加轻量 `AgentRunner`、角色注册和工具注册。每个角色执行有上限的“读取任务 → 选择允许的工具/提交结果 → 读取工具返回 → 判断下一步”循环，支持多个任务实例并行。

现有 `LlmClient.complete()` 只返回文本，不能直接提供工具调用。需要新增并验证结构化决策协议：优先适配模型实际支持的工具调用；兼容文本模型时，严格解析和验证 `call_tool / complete / needs_input` 等有限 JSON 决策，失败时进入有上限的修复或明确降级，不执行任意自然语言。是否支持该协议通过实际模型能力测试确认，不能仅凭模型名称推定。

初版各角色可共用默认模型档案，角色之间仍保有不同工具、上下文和任务目标。是否分配不同模型由后续准确率、延迟和成本评测决定，不把购买多种模型当作多 Agent 的必要条件。

#### 7.8.3 并发、持久化与失败恢复

- 初始可采用“每个目标最多 3 个并发 Agent 实例”的保守可配置值；此数值是起始配置建议，不是实测最优值。全服务还需设模型并发与队列上限。
- 现有 `ingestionExecutor` 已有独立并发与队列配置。Agent 调度不能长时间阻塞该线程池，也要把 OCR、抽取和复审内部模型请求纳入全局额度协调，避免表面三个 Agent 实际触发几十个并发模型请求。[E19]
- 同库中不同资料的只读研究可并行；同一节点、任务或学习路径的写入经过统一执行器和领域版本校验。模型推理期间不持有数据库事务锁。
- 为明确提交的业务协作目标保存最小结构化目标、依赖、对象 ID、必要成果引用、执行回执和检查点；聊天原文与模型中间对话默认不保存。短暂问答与未提交的分析随关闭清理。
- 进程重启后先查询既有领域任务是否已执行，再恢复未完成步骤。没有足够持久化输入的临时研究不得宣称可以无损续跑；需标为中断并明确重新发起入口。
- 一个 Agent 失败不必取消独立兄弟任务；依赖它的步骤等待恢复或显示“前置失败”。总控可以交付部分成果，但必须列出尚未完成的部分。
- 停止协作会禁止新步骤、请求取消在途步骤；已经写入的业务数据保持可查询，并明确哪些任务仍在运行、哪些操作已经完成。

#### 7.8.4 分歧、质量与成本控制

Agent 结论冲突时，先比较范围、数据版本和原文证据；必要时安排一次针对争议点的补查。初版设置有限的复核/改写次数，超过预算仍未解决时保留分歧并请用户选择需要进一步处理的对象，不通过无限互评或简单多数投票把不确定结论包装成事实。

质量治理 Agent 的检查是辅助证据审查，不代替引用 ID 验证、参数校验、正式判分和数据库约束。生成方和复核方可以共享来源，但复核方应重新读取关键来源，而不是只接受生成方的摘要。

每个目标同时限制任务数、模型调用次数、输入/输出预算、工具调用次数与最长耗时；限流时由全局调度退避，避免所有角色一起重试。预算耗尽返回实际已完成成果与缺口。工具失败不能用生成内容补成“成功”。

相同范围与版本的只读查询可以在本任务内复用；不同权限范围和不同版本不共用缓存结果。仅有一条状态查询或短知识问题时选择单角色/直接工具路径，复杂比较、跨模块目标再启用多角色协作。

这些架构模式参考了关于动态分工、独立上下文及协调成本的工程实践；本项目的角色划分、预算和落地顺序是基于本地代码作出的设计判断，性能收益尚待验证。[多 Agent 研究系统实践](https://www.anthropic.com/engineering/multi-agent-research-system) 中同时讨论了并行收益与成本、依赖协调问题；[Agent 与工作流的区分](https://www.anthropic.com/engineering/building-effective-agents) 用于明确本方案中动态 Agent 和确定性业务流程各自的责任。

## 8. 实施顺序与交付门槛

采用四个工作包。W0/W1 即建立多 Agent 核心和可验证的协作场景，再逐步扩大执行能力，不能先做成单一聊天助手后将角色名称当作多 Agent 交付。工作量需要在实现前结合当前在途功能合并状态估算，本规划不虚报确定工期。

| 工作包 | 核心交付 | 进入下一阶段的门槛 |
|---|---|---|
| W0：协作契约与现状校正 | 确定总控+五角色；实现任务/工具/成果契约及调度原型；明确来源分层、临时对话与范围；梳理自动入库副作用和学习完成规则 | 至少一个模型能够可靠执行有限工具决策；任务有依赖、完成条件与预算；不能伪造工具成功 |
| W1：全流程查询与多 Agent 协作 | 接入所有模块上下文；上线无节点可用的助手工作区和协作任务视图；五角色接入各自读取/草稿能力；实现跨资料并行研究→质量复核→学习建议 | 全流程矩阵每行至少一个场景通过；能够验证两个实例独立取证、成果交接与依赖执行。未开放写入如实说明 |
| W2：操作与学习闭环 | 统一操作执行/幂等/状态回查；多 Agent 接续现有处理链；路径版本；正式测评服务端计分；持久任务恢复与停止后续步骤 | 多角色协作完成“准备 → 导入 → 处理 → 入库 → 探索 → 路径 → 测评 → 复习”，业务结果与原模块一致 |
| W3：质量与交互增强 | 比较单角色与多角色效果；检索评测、流式反馈、复杂研究、批量建议、移动端与可访问性完善；按证据优化模型路由与并发 | 同一问题集评估质量/耗时/调用量，能够说明何时需要团队；失败可恢复，无跨范围污染或重复执行 |

W1 是全流程基础版；W1 + W2 才达到本次要求的完整模块。不能只完成聊天页改版就宣称“覆盖整个项目流程”。W3 中的流式、复杂推理和推荐增强不作为拖延核心流程覆盖的理由。

## 9. 验收方案

以下均为后续实现验收，不是本次已经执行的测试。

### 9.1 核心业务场景

| 编号 | 场景 | 必须满足 |
|---|---|---|
| T01 | 空项目首次进入助手 | 无需节点即可获得配置、建库、导入指引；无模型时指引仍可用 |
| T02 | 同名概念出现在两个库 | 选择库 A 只使用 A 的可用来源；显式跨库比较才纳入 B，并分别标明来源 |
| T03 | 未完成解析的资料 | 准确说明阶段；可检查已准备单元，不把未复审候选当成正式知识 |
| T04 | 上传并处理一份测试资料 | 导入、处理、自动复审/入库范围说明一致；可回到处理中心查真实任务，无重复任务 |
| T05 | 任务失败后建议重试 | 依据错误和候选/检查点状态说明重跑范围；受理与完成分开显示 |
| T06 | 解释被拒的候选关系 | 展示对应候选、原文和复审原因；建议文本不会自动修改审核结果 |
| T07 | 询问关系方向与两跳路径 | 主体/客体正确；两跳有路径和中间节点；截断时说明不完整 |
| T08 | 点击资料引用 | 请求完整单元，以稳定 ID/版本高亮 chunk；删除、重新解析或失效时给可理解状态，不错配新分段 |
| T09 | 连续追问“它/两者/继续” | 在当前范围正确解析；歧义时选择对象；历史引用不串到新证据 |
| T10 | 相关但资料未直接覆盖的问题 | 允许补充讲解，并明确和原文事实区分；不伪造出处 |
| T11 | 生成/调整学习路径 | 预览范围、顺序和变更；调整保留历史；替换效果明确 |
| T12 | 正式测评数据不足或提交失败 | 不静默使用通用题推进当前阶段；结果未保存时不能宣称阶段完成 |
| T13 | 提交正式作答、重复提交、阶段已变化 | 服务端判分，绑定原试卷与阶段，重复提交不重复推进，新阶段不会误收旧成绩 |
| T14 | 分析进度与薄弱点 | 来自有效测评与阶段记录；没有数据时说明不足，不生成虚构掌握率 |
| T15 | 用户只要求“解释这个概念” | 不触发 AI 搜索扩展入库；正式新增明确目标库和 AI 来源 |
| T16 | 操作超时/断网后重试 | 先查询原执行结果；幂等处理；不重复入库、创建路径或推进阶段 |
| T17 | 恶意文档要求执行删除或泄露设置 | 作为普通资料处理，不形成工具授权，不返回模型密钥 |
| T18 | 关闭、换范围、重开、刷新 | 对话与草稿按既有决策清空；已受理业务任务仍可在原模块查询 |
| T19 | 手机和桌面切换、查看原文 | 同次打开不产生两个请求实例；原文查看不意外清空对话；焦点/键盘/滚动可用 |
| T20 | 模型认证失败、限流、超时、后端离线 | 区分错误类型、提供恢复入口；不能将模型不可用描述为所有功能不可用 |
| T21 | 数据洞察解释 | 统计数和范围与接口一致；有限样本不冒称全量；无历史数据不生成趋势结论 |
| T22 | 操作预览后对象被别处修改 | 服务端发现状态/版本变化，拒绝旧计划并刷新影响；不应用过期修改 |
| T23 | 修改资料元数据、归档资料、查看人工核验 | 标题/标签更新可验证；归档后的取材遵守范围与状态规则；AI 分析不会自动写成人工已校对，未开放动作不显示虚构入口 |
| T24 | 两份资料并行研究并汇总比较 | 独立任务实例与来源范围可查；聚合结果覆盖双方证据；同名引用不串号，页面分工显示真实状态 |
| T25 | 研究→质量核查→学习建议接续 | 下游使用前置成果与有效版本；前置不足时等待/说明限制；不会在没有资料时虚构已完成研究 |
| T26 | 两个 Agent 提出冲突修改 | 统一执行器识别同对象竞争，应用版本校验，不能出现最后写入者静默覆盖前者 |
| T27 | 一个子任务失败、模型限流或预算耗尽 | 独立任务成果保留；依赖步骤状态准确；有限重试/补查；返回部分结果及缺口而非假装全部完成 |
| T28 | 用户关闭聊天、停止协作、服务重启 | 临时对话清空；已提交业务任务按真实状态回查；停止不再分派新步骤；不可恢复的临时研究如实标记 |
| T29 | 专业 Agent 越界或模型输出非法工具决策 | 注册表与参数/范围校验拒绝执行；子 Agent 无法自行扩大权限或无限创建团队 |
| T30 | 简单问题与复杂目标分流 | 简单问题不必启动全部角色；复杂目标有真实拆解与交接；记录单角色/多角色质量、耗时和模型调用量 |

### 9.2 质量与验证方式

- 先复用并扩展已有 ChatController、ChatService、RetrievalService 和 LlmClient 测试，覆盖契约兼容、范围、方向、引用和错误；本次未运行这些测试。
- 业务写操作和学习状态机在隔离测试数据上验证幂等、冲突、事务和恢复；不能借验收重跑用户生产资料。
- 建立项目真实主题的小型问题集，至少覆盖单节点、跨节点、跨资料、指代、资料不足、来源冲突和处理状态；分别记录命中来源、答案依据、误引用和是否给出有效下一步。
- 上线门槛包括：T01–T30 全部通过；测试范围内无未授权写入、无重复推进、无跨选定范围取材；有效引用全部能定位。答案质量由样例逐条审查，不把“引用 ID 存在”等同于答案正确；角色名称和并发动画不构成协作成功证据。
- 性能记录查询、检索、模型生成各段耗时及超时率；先建立真实环境基线再定 p95 目标，不用无依据的“秒回”承诺。
- 页面完成后开展浏览器验收：窄屏/桌面、深色模式、键盘与输入法、长回答、长引用、错误/重试、关闭重开、断点切换和软键盘。

## 10. 本次规划的最终决策

1. 智能助手升级为项目级多 Agent 协作工作区，采用总控加五个专业角色，覆盖知识建设和学习应用两条主线。
2. 以显式上下文、真实业务状态和可追溯来源为基础，而非只扩展提示词。
3. 同一能力内核服务独立页与各模块侧栏；保留临时对话，不默认建设历史聊天系统。
4. 早期即实现真正的任务拆解、独立工具循环、并行研究和成果交接；随后完成受控操作与可靠学习闭环。有既有入口的高风险动作首版可通过原模块完成。
5. 正式成绩、路径历史和自动入库副作用属于基础边界，必须在接入助手操作前处理清楚。
