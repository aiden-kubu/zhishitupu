## 5. 查询语义必须保持的约束

1. 仍只支持既有项目范围或知识库范围；带资料/节点约束而不支持的洞察范围仍须在 JDBC 前拒绝，不能扩大授权范围。
2. 先确定授权的 `visible_nodes` 和 `visible_edges`，再统计和排序。多库范围是被选中知识库的并集；共享节点不能重复计数。
3. 现有可见节点查询没有按节点 active 状态排除节点，不得在性能补修中新增过滤。
4. 边必须 active，且两端均在可见节点内。跨两个已授权知识库的边可计数；连到范围外节点的边不能计数。
5. 度数是“接触当前节点的边记录数”，不是独立邻居数。自环计一次；反向边分别计数；同端点不同关系类型的边分别计数。不能把两个端点简单相加导致自环翻倍，也不能用 DISTINCT 邻居导致少计。
6. 无边节点仍出现在可见节点集合，度数为 0；排名容量足够时可进入结果。排序仍为度数降序、节点 ID 升序；LIMIT 在范围过滤和计数之后。
7. 节点名称/类型/ID、返回结构、统计口径、截断口径及非排名字段不变；使用数值 ID，不新增 Long 对象身份比较。
8. 不把多条独立 SELECT 宣称为一致性快照，不顺带改变并发一致性契约。

可评估的逻辑方向：对已过滤边生成端点流，source 端点保留，target 端点仅在不同于 source 时保留；使用 `UNION ALL` 后按 node_id 聚合，再与可见节点 LEFT JOIN，缺失度数取 0，最后排序及 LIMIT。

这是待验证方案，不是已验证 SQL，也不要求机械采用。它旨在消除逐节点反复扫描边的相关计数；不宣称 MySQL 一定只物理扫描一次。具体执行计划与性能必须由真实实例确认。

## 9. 停止条件与非目标

遇到以下情况停止相关操作并报告，不自行扩大范围：

- 主项目/原工作树目标文件前像不同、发现来源不明的修改，或需要改变公共/领域契约。
- 新方案无法保持自环、共享节点、边状态、范围或排序口径。
- 排名修复后其他查询成为瓶颈，需要扩大 SQL 修改、改索引、迁移或提高预算。
- 实例 UUID、版本、端口、联接目标、库名不符，账号权限超出批准范围。
