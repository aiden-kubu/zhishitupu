## 阶段规则

1. 原五个任务已经存在，保持原任务、原工作树，不重建、不替换。任一时刻最多一个子任务执行被指派阶段；禁止自行派生 Agent 或同时启动其他任务。
2. W0、W1 及既有验收结论是历史基线，不能据此自动进入下一阶段。每阶段及每次扩大修复范围均须获得负责人授权。
3. 领域 Bug、性能问题、测试缺口及补修统一走：总控分析 → 编写定向任务单 → 负责人手动转发原任务 → 接令检查并停止 → 另获正式执行授权 → 原任务实施/测试/汇报后停止 → 总控复核 → 获授权后受控汇集/统一回归/真实环境复验 → 负责人最终验收。
4. 总控复核不通过时编写补修指令退回原任务，不自行修掉问题。不能因工作树可访问、修复量小或跨任务派发不可用而代做。
5. 任务单须指定实际执行任务、工作树/分支、允许文件、只读依赖/前像、契约约束、测试计划、模型要求、报告路径和停止条件；接令检查不是开发或数据库连接授权。
6. 遇到新的 SQL 瓶颈、未知修改、前像不符、公共接口冲突或归属争议，停止相关操作并报告，不自行扩大 SQL、索引、迁移或其他领域范围。
7. 报告须区分实际修改者、实际测试运行者、总控集成验证者、模型要求与实际核实状态；不把工作树名、文件 owner、任务单抬头或过去模型回执当作当前执行者证明。
8. 模型不可用或额度不足时如实报告并停止调度，不私自换模型、降低推理强度或绕过限额。

## 增量审查与指令标识（2026-09-28 补充）

- 已完整阅读/审查且内容未变化的文档、代码、测试结果和证据，直接引用已有结论；包括总控自己刚生成并完成必要校验的文档，不重复全文审查。
- 变化时只检查差异及影响范围。接口、依赖、权限、表结构、环境或样本变化可能使相关未改代码的旧结论失效，届时说明原因后扩大；基线缺失、未知修改或上下文无法可靠恢复时，补足必要阅读，不默认从头审查全项目。
- 以版本/hash 或明确补丁绑定旧结论；不能只看 git diff 漏掉未跟踪文件。轻量核对前像与全文质量审查分开，不在每次小文档更新时默认扫描全仓；正式汇集所要求的保护检查仍保留。
- 文档复用不豁免受影响代码的回归测试。报告区分“复用结论”“本次差异及影响”“扩大原因”“本次实际验证”，不得把未重跑的测试写成当前新验证。
- 总控输出必须明确标为“给负责人：范围汇报/待批准”“给原任务：接令检查（只读）”或“给原任务：正式执行（须负责人明确授权）”。不要把范围汇报混写成派发令。接令检查完成一次即汇报停止，收到相同且未变化的内容不重新检查；“继续/开始”如未指明升级授权，不自动扩大到开发。
