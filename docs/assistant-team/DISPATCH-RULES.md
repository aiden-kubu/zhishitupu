## 默认流程

总控分析/审核并准备任务 → 负责人批准 → 对应原 01～06 正式执行 → 完成后总控审核 → 负责人决定验收或下一步。

申请批准前，总控须明确七项：执行者、任务范围、允许修改文件、前像/基线、验收标准、安全边界、停止条件。批准绑定具体任务及版本/清单，不是无限期授权。

任务获批后，发给原任务的默认就是“正式执行指令”。不再安排“无阻塞只读接令 → 回来等同一任务第二次授权”；总控也不得在既定条件已满足时因旧惯例新增停点。尚未批准的方案标为待批准，不能冒称正式授权。

## 执行前门禁

门禁属于正式执行的一部分。只核对必要的实际工作树/分支、直接文件前像及目标占用、环境/权限、任务范围和授权。复用未变审核结论，不重复全量阅读、全仓扫描或测试。

- 与获批基线一致、无阻塞：直接完成获批工作，不停在“等待正式执行指令”。可简短通报门禁通过，随后继续。
- 普通测试覆盖缺口：若不影响安全、不扩大权限、不改变数据/索引/契约，记录未覆盖并继续其余已批准项目；依赖项标阻断，不整批重新索取执行授权，不为消除缺口擅自补样。需要改变数据、索引、迁移、契约、预算或权限等，才停止相关操作申请。
- 实际变化、未知修改、前像不符、范围冲突、安全风险、必要授权缺失：停止受影响操作并报告具体差异、影响及最小待决定事项；不得自行修正前像、忽略异常、扩大权限或替换任务。
- 门禁本身不能实施尚未获批的数据库连接、样本写入或其他外部操作。已批准的真实复验可按任务单先做环境身份/权限核验，不能把该正常门禁再次当作需要授权的独立任务。

## 单独只读接令的例外

仅在新建任务首次接手、跨领域/高风险任务、基线不明确、环境或权限发生变化、历史成果需要接管，或总控说明必须先检查的具体原因时设置。

总控应写清风险是什么、为什么不能纳入正式执行前门禁、最小检查范围、检查后的决策点。不能仅贴上“高风险/跨领域”标签就把普通同一任务续作、补修、复验恢复成两次授权。真正只读接令依旧只读、完成停止；没有开发/真实环境授权时不能借此直接执行。

## 正式任务的指令格式

1. 标题：“给原 XX：正式执行”；注明负责人批准的任务版本、范围和来源，不伪造已批准。
2. 列出七项任务要素、只读依赖、证据/报告落点，以及模型要求与既有桌面确认依据。
3. 明确：“执行前门禁一致就直接执行；只有实际变化、冲突、安全风险或缺授权才停报。”
4. 明确独立失败/依赖阻断/安全异常的处理，以及完成后停止、交总控审核。

负责人批准并人工转发后，原任务即可在该范围执行。没有可靠桌面控制入口时继续人工转发，不新建 App Server、不用临时 Agent 代替原任务、不由总控进入领域工作树代做。

## 不变的所有权与安全边界

- 总控负责规划、任务单、所有权/依赖和增量审核；不代做领域代码。01 ingestion/source、02 quality、03 research、04 learning、05 assessment 保持原所有权。
- 06 负责明确获批的受控汇集、统一回归、真实环境/性能/零写入验证、证据和收尾，不修改 01～05 领域实现或领域测试，不用集成辅助逻辑重写业务。
- 原 01～06 严格串行，获批测试进程内部并发除外；一次任务批准不自动授权另一个执行者或下一阶段。
- 发现范围外事项停报；不擅自改变索引、迁移、契约、权限、数据、预算、测试标准或保护规则。
- 已知历史证据/hash 不倒改。技术审核不等于负责人验收；不自动继续其他 I2、I3、W2 或未获批阶段。
- 模型要求和用户确认/工具核实分列规则不变；任务报告写实际作者、汇集者、测试与真实环境执行者、总控审核者。
